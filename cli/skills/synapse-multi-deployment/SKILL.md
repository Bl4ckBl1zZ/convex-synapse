# Multiple deployments per project

A Synapse project can host any number of Convex deployments. The
**three types** mirror Convex Cloud's model:

| Type | Convention | Typical use |
|---|---|---|
| `dev` | Operator's personal sandbox (1 per developer is fine) | Day-to-day coding with hot-reload |
| `prod` | The live, customer-facing one (1 per project, usually) | What the production app hits |
| `preview` | Short-lived branches / PR previews | CI spins up + tears down per branch |

"One PROD per project" is a strong convention but it is **not**
enforced at the DB or API level — the `deployments` table only has
`UNIQUE (name)` + `UNIQUE (host_port)`. What's enforced is that at
most one deployment per project can carry `isDefault=true` for a given
type; the dashboard and CLI assume the default-PROD is "the" prod.
You can have many `dev` and `preview` deployments freely.

The `.synapse/project.json` in the cwd stores which DEV + PROD
deployment names the CLI should target by default (see `synapse select`).

## The "active" deployment concept

`synapse dev` always targets the **DEV** linked in `.synapse/project.json`.
`synapse deploy` always targets the **PROD** linked there. To switch
which DEV or PROD the CLI uses:

```bash
synapse select
```

Walks an interactive picker: team → project → DEV (lists all dev deps
in that project) → PROD (lists all prod deps; default is the only one).
Auto-selects when there's exactly one option.

## See what's available

```bash
synapse status              # all deployments in this project, with URL form
synapse status --json       # machine-parseable
synapse list deployments    # alternative, no project linking needed (uses CWD)
synapse list deployments --project=<id>  # cross-project lookup
```

Sample output:
```
Project: amagejumpy
NAME                 TYPE   STATUS    FORM       URL
brave-dolphin-1060   DEV    running   wildcard   https://brave-dolphin-1060.app.synapsepanel.com

lush-heron-4656      PROD   running   wildcard   https://lush-heron-4656.app.synapsepanel.com
```

## Creating a new deployment

```bash
synapse deployment create                  # defaults to --type=dev
synapse deployment create --type=prod
synapse deployment create --type=preview
synapse deployment create --type=preview --default --project=<uuid>
```

- The deployment NAME is auto-generated by the backend (`<adjective>-<animal>-<digits>`).
- Flags: `--type=<dev|prod|preview|custom>`, `--ha`, `--default`,
  `--project=<id>`, `--yes`. There is no `--reference` / `--name` flag
  — the backend owns the name and there is no "tag" column.
- `--type=custom` is a real, accepted value (used when you adopt /
  attach an external Convex backend); for greenfield work the three
  common types are dev / prod / preview.
- Returns immediately with `status: provisioning`; the container takes
  ~3 seconds to be ready. Watch readiness:
  `synapse deployment status <name> --watch`.

After creating, run `synapse select` to point `.synapse/project.json` at
the new deployment if you want subsequent `synapse dev` / `synapse deploy`
calls to use it.

## Pushing code to a SPECIFIC deployment (not the one in project.json)

The default `synapse dev` / `synapse deploy` use the linked deployments.
To override per-invocation:

```bash
# Option A — switch the link, then run normally
synapse select   # pick the deployment you want as DEV (or PROD)
synapse dev

# Option B — invoke convex CLI directly with synapse-injected creds
synapse credentials <deployment-name> --format=shell > /tmp/creds.sh
source /tmp/creds.sh
npx convex dev   # now uses those creds
```

Option B is the escape hatch for CI scripts that target many
deployments without re-linking each time.

## Preview deploy CI pattern

Goal: every PR gets a fresh Convex backend at a stable URL the
preview app can hit.

```bash
# In CI, with SYNAPSE_APP_TOKEN (per-project preview key) in env:
PREVIEW_NAME=$(synapse deployment create --type=preview --json \
  | jq -r .deployment.name)
# (To tie the deployment to a PR, persist the PR_NUMBER → PREVIEW_NAME
# mapping in your CI's own state; Synapse has no per-row label field.)

# Get creds for the new preview
synapse credentials "$PREVIEW_NAME" --format=shell > /tmp/preview.env
source /tmp/preview.env

# Push code to it
npx convex deploy

# Echo URL for the preview app's env
echo "NEXT_PUBLIC_CONVEX_URL=https://${PREVIEW_NAME}.app.synapsepanel.com"

# On PR close, tear down
synapse deployment delete "$PREVIEW_NAME" --yes
```

App tokens are the preferred CI credential — see the dashboard's
"Project Settings → Access Tokens → App tokens" section to mint one.

## Convention notes

- **Don't mix `dev` and `prod` in one developer's `synapse select`**.
  Each dev should pick their own DEV (e.g. `brave-dolphin-1060` is
  Ian's, `sunny-dolphin-1178` is Matheus's) and share the same PROD.
- **PROD push needs typed confirmation** — `synapse deploy` always
  prompts unless `--yes` is passed. The dashboard's Delete Project /
  Delete PROD-deployment flows use a typed-name confirmation (GitHub-style).
- **Preview deploys are billed the same as dev/prod** by Synapse (you
  own the VPS). Don't be shy about creating them per-PR — just clean up.

## Quick reference

| Goal | Command |
|---|---|
| Show all deployments + statuses | `synapse status` |
| Switch active DEV / PROD | `synapse select` |
| Create new deployment | `synapse deployment create --type=<dev\|prod\|preview>` |
| Watch a deployment until ready | `synapse deployment status <name> --watch` |
| Delete a deployment | `synapse deployment delete <name>` |
| Push code to currently-linked DEV | `synapse dev` |
| Push code to currently-linked PROD | `synapse deploy` |
| Use a specific deployment without re-linking | `synapse credentials <name> --format=shell` + `source` + `npx convex …` |
