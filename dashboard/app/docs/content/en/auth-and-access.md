# Auth and Access

Synapse uses email + password as the only first-party login method. Sessions are short-lived JWTs; longer-running automation (CLI, CI, scripts inside the dashboard) uses opaque personal access tokens (PATs) that start with `syn_`. There is no SSO, no SAML, and no WorkOS — OIDC is on the roadmap.

## Registration

`POST /v1/auth/register` with `{ email, password, name }`.

- Email must contain `@`; the column is `citext` so casing collisions are caught (`Alice@example.com` and `alice@example.com` are the same row).
- Password must be at least 8 characters, stored as a bcrypt hash via `auth.HashPassword`.
- Duplicate email returns `409 email_taken` — detected by SQLSTATE 23505 on `users_email_key`.

**The first user to register becomes the instance admin.** The INSERT uses `NOT EXISTS (SELECT 1 FROM users)` to set `is_instance_admin = true` automatically on the first row, and a `pg_advisory_xact_lock(hashtext('synapse:first_instance_admin'))` serialises that decision.

Instance admins are the only accounts allowed to hit `/v1/admin/*`. They are not automatically admins of any team; team-level admin is a separate `team_members.role` row.

Response: `{ accessToken, refreshToken, tokenType: "Bearer", expiresIn, user }`.

## Login

`POST /v1/auth/login` with `{ email, password }`. Same response shape. Records an `audit.ActionLogin` event. Wrong credentials always come back as `401 invalid_credentials` — no distinction between "no such email" and "wrong password".

## JWT lifetimes

HS256, signed with `SYNAPSE_JWT_SECRET`. Two kinds, both carry a `kind` claim:

| Token | Default TTL | Override |
|---|---|---|
| Access | 24 hours | `SYNAPSE_JWT_ACCESS_TTL` |
| Refresh | 720 hours (30 days) | `SYNAPSE_JWT_REFRESH_TTL` |

The refresh path (`POST /v1/auth/refresh`) verifies the `kind` claim is literally `"refresh"` and mints a new pair. The dashboard does not implement silent refresh today; the 24-hour access TTL is generous enough that most operator sessions just survive on the access token.

## Personal access tokens (PATs)

Opaque random bytes — not JWTs — generated by `auth.GenerateToken`:

- 256 bits of entropy from `crypto/rand`
- base64url-encoded and prefixed with `syn_` (helps GitHub-style secret scanners spot leaks)
- stored as a SHA-256 hex digest in `access_tokens.token_hash`; the plaintext is returned **once** at creation

Use as a bearer credential: `Authorization: Bearer syn_<rest of token>`.

The auth middleware accepts both JWTs and `syn_*` tokens on the same routes. PATs update `access_tokens.last_used_at` and carry their scope into request context.

### Managing PATs from the dashboard

The personal token panel lives at `/me` (`dashboard/app/me/page.tsx`). Backing routes (registered directly under `/v1`):

- `POST /v1/create_personal_access_token` — `{ name, scope?, scopeId?, expiresAt? }`
- `GET /v1/list_personal_access_tokens` — paginated, metadata only
- `POST /v1/delete_personal_access_token` — `{ id }`

Scoped tokens have their own create/list endpoints under the resource itself: `POST /v1/teams/{ref}/access_tokens`, `POST /v1/projects/{id}/access_tokens`, `POST /v1/projects/{id}/app_access_tokens`.

## PAT scopes

Every PAT carries one of five scopes:

| Scope | scopeId | Where it's created | What it can do |
|---|---|---|---|
| `user` | none | `/me` | Anything the owner can do via dashboard JWT (default) |
| `team` | team id | `/teams/<slug>/settings/access-tokens` | Anything inside that one team |
| `project` | project id | `/teams/<slug>/<project>/settings/access-tokens` | Anything inside that one project |
| `app` | project id | Same place as `project` | Same surface; separate label for "App tokens" UI |
| `deployment` | deployment id | CLI deploy keys panel | One deployment only |

## Scope hierarchy

A scoped token can act on a target at its own level or below, never above:

|        | Y = team | Y = project | Y = deployment |
|--------|----------|-------------|----------------|
| user   | yes      | yes         | yes            |
| team   | exact    | child       | child          |
| project / app | no | exact       | child          |
| deployment    | no | no          | exact          |

Mismatch returns `403 forbidden_token_scope`. JWT-authenticated calls and `user`-scoped PATs bypass the gate entirely.

## Revocation

Delete the row. From the dashboard: open `/me`, find the row, hit "Delete". From the API: `POST /v1/delete_personal_access_token { "id": "<token-id>" }`. The next request bearing that token will fail at the auth middleware before reaching any handler.

There is no "rotate" verb — create a fresh token, paste it into your CI / scripts, then delete the old one.

## What about SSO / OIDC?

OIDC is on the roadmap but not yet shipped. Synapse stays email + password JWT until then; the operator owns the auth boundary completely (no WorkOS, no SAML, no third-party identity providers).

For now, the practical pattern for teams:

1. Each operator registers individually at `/login` (or accepts a team invite — see teams-and-projects).
2. Long-running automation uses a `team`- or `project`-scoped PAT, not a personal one, so it survives the human leaving.
